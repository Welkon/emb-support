# 正点原子 DP100（DP100 数控电源）

## 官方规格

来源：本机资料包 `~/【正点原子】DP100数控电源/`

- `DP100数控电源用户手册 V1.2.pdf`
- `2，DP100 Digital Power Supply/DP100 Digital Power Supply User manual.pdf`
- `2，DP100 Digital Power Supply/2，PC Software/ATK-DP100 DLL user manual.pdf`
- 固件 `DP100_V1.0.atk` ~ `DP100_V1.4.atk`

关键参数：

| 项目 | 值 |
|---|---|
| 输出 | 0–30.00 V，0–5.000 A，100 W max |
| 设定分辨率 | 10 mV / 1 mA |
| 输入 | DC 5.0–32 V（PD/QC 或直流） |
| 保护 | OVP / OCP / OPP / OTP / REP / UVP |
| OVP 范围 | 0.00–30.50 V |
| OCP 范围 | 0.000–5.050 A |
| 过功率保护 | ≤105.0 W |
| 过温保护 | 50–80 °C |
| 预设组 | 0–9（每组含 V/I/OVP/OCP） |

注意：DP100 是**降压**电源，输入电压必须高于输出电压；资料包明确要求
“DP100 工作在降压模式，需要保证输入电压高于输出电压”。

## 协议

USB HID，VID:PID `2e3c:af01`，64 字节报告：

```
FB op 00 len <data> crc16_lo crc16_hi     # host -> device
FA op 00 len <data> crc16_lo crc16_hi     # device -> host
```

CRC16-Modbus（poly 0xA001，init 0xFFFF）。opcode：

- `0x10` 设备信息（型号、固件、序列号）
- `0x30` 实时遥测（Vin/Vout/Iout/vo_max/温度/输出模式/工作状态）
- `0x35` 设定/输出（子命令 `0x20` + 输出位 + V/I/OVP/OCP，单位 mV/mA）
- `0x40` 系统信息（背光、过温阈值、蜂鸣器）

协议实现参考：

- `lymzzyh/dp100-mcp`（MIT）：完整 opcode、解析和 CRC
- `weigu1/dp100_manipulator`：独立实现的抓包与字段偏移验证

## 协议核对

官方 DLL 是 .NET 程序集，但静态 IL 经过混淆：`FrameEntity.CRC16` 反编译后只是
`ldc.i4.0; ret`，`SendCmd` 返回 null，真实逻辑在混淆方法里（`dataEncription` 等）。
因此没有继续反编译，而是用两个独立开源实现 + 实机抓包交叉验证：

| 帧 | 含义 | 实机抓包（weigu1） | 本 skill |
|---|---|---|---|
| `fb 10 00 00 30 c5` | 读设备信息 | 一致 | 一致 |
| `fb 30 00 00 31 0f` | 读实时信息 | 一致 | 一致 |
| `fb 35 00 01 80 ce 28` | 读当前预设 | 一致 | 一致 |

CRC16-Modbus(poly 0xA001, init 0xFFFF, xor 0) 也逐字节一致。

注意：`weigu1` 的解析里把 16 位小端值写成 `hi*255+lo`，应为 `hi*256+lo`；
本 skill 用后者（与 `lymzzyh/dp100-mcp` 和 16 位小端定义一致）。

## 官方 DLL 的保护与静态分析

对 `ATK-DP100DLL(x64).dll` 做了静态检查（dnfile/dncil + capstone）：

- `file`：`PE32+ ... Mono/.Net assembly`，确认为 .NET 程序集。
- 类型/方法名被混淆；`kgbOBx7BanbFa22Hp9` 里有一个 5976 条 IL 的
  **IL 虚拟机**：`CcHZl53jD` 是 dispatch 循环，同类型的 `UIU7PIr5u` /
  `k0Yp08bI2` / `SLEBa6at2` 是 `add/xor/and/or` 等 VM handler，
  并引用静态表 `0x0400010C`；`.cctor` 里还有绝对地址 `switch`（非法 IL），
  属于反反编译设计。
- `MethodImpl` 把 `Finalize` 指向 **native MemberRef**；`FieldRVA` 里是
  x86 跳板（`push ebp; ...; jmp eax`），跳转目标是运行时才解析的地址。
- `CMDEncryptDecode` 的静态字段（ILSpy 反编译确认）：`frameSize=64`、
  `encriptionConst=30`、`encriptionByteLoc=0`、`encriptionData=0`；
  `.cctor` 用 switch 状态机初始化这四项。
- 公开方法 `CRC16` / `CalculateCheck` / `SendCmd` 的 IL 是
  `nop; ldc.i4.0; ret` / `ldnull; ret` —— **stub**，真实实现被加密或放在 native 段。

结论：这是商业级 .NET 保护（native stub + 方法加密 + IL 虚拟化，
接近 .NET Reactor 的特征）。我把 764 个方法、15439 行 IL 全部 dump 到
`/tmp/dp100_il.txt` 核对过：公开方法只剩 stub，真实逻辑在 VM handler 和
native 跳板里；de4dot/ILSpy 也恢复不了，静态路线到此为止。
**不建议也不需要在本地破解**。

协议正确性以两条独立证据为准：

1. 两个开源实现（`lymzzyh/dp100-mcp`、`weigu1/dp100_manipulator`）的
   实机抓包/代码；
2. 本 skill 生成的帧与 `weigu1` 的实机抓包逐字节一致（见上表）。

`CMDEncryptDecode` 表明官方协议存在一套“数据段加密”机制，但普通
遥测/设定帧在实机上以明文工作，说明该机制只用于文件/固件传输
（`sendUsbDataByBytesofFile`、`dataPkgEncriptionWithFrameSizeAlign`）
或特定模式，不影响本 skill 的基本控制。

Linux 上可用的反编译工具：`ilspycmd`（已在本机 `~/.dotnet` 安装）或
AvaloniaILSpy；dnSpy/dnSpyEx 只有 Windows。它们能读到公开方法和 `.cctor`，
但对这份 DLL 只能看到 stub——真实逻辑由 VM/native 在运行时替换。

如果要 100% 确认所有模式：在 Windows 上跑官方上位机，用 USBPcap +
Wireshark 抓 HID 报文，对比 `set/measure` 帧即可；这比破解 DLL 更快也更稳。

## 本 skill 的行为

- 打开时读取设备信息与 `vo_max`（受输入电压限制），再读取当前预设；
- `set` 会同时下发 V/I/OVP/OCP 和当前输出状态（DP100 协议要求整包写）；
- 电压/电流分别限制在 30 V / 5 A，OVP ≤30.5 V，OCP ≤5.05 A；
- `measure` 读 `0x30` 的 Vout/Iout，功率由 V×I 计算；
- 输出状态读 `out_mode`（1=ON）。

## 未覆盖

- 预设组（0–9）的读取/切换；
- 过功率/过温/反接保护的系统参数设置；
- 固件升级（`.atk` 文件）；
- 多台串联（≤3 台）的主从配置。

这些都可以通过 `scpi` 之外的专用 HID 命令扩展；当前聚焦“设压设流、开输出、测量、保护”。
